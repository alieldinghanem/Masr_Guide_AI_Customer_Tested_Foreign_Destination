# Masr Guide AI v7.5 — Proactive Reliability & Security Report

**الهدف:** تقليل المخاطر غير المكتشفة قبل عرض المشروع أمام HR أو فتحه لمستخدمين حقيقيين. **لا يمكن ضمان عدم ظهور مشاكل جديدة مستقبلًا**. جميع نتائج هذا التقرير تخص الكود المحلي من دون اتصال حي بخدمات Gemini أو اختبار متصفح نهائي.

## التغييرات البرمجية المنفذة

1. `backend/app/security.py`: منع إساءة استخدام التسجيل/الدخول/طلبات الشركاء ولوحة الإدارة عبر Sliding Window Rate Limiter مع `429` و`Retry-After`، وحد أقصى لذاكرة تتبع المصادر. هذه حماية إضافية محلية لا تحل محل Rate Limiting عند الـProxy في بيئة متعددة العمال أو الخوادم.
2. `backend/app/main.py`: Middleware يطبق حماية نقاط الدخول، رؤوس `nosniff` و`DENY`، و`no-store` لمسارات الحساب والإدارة، وفحص Content-Length أكبر من 512KB. يتطلب حماية حجم الطلب أيضًا عند الـReverse Proxy للطلبات دون Content-Length.
3. `frontend/nginx.conf`: حد أقصى 512KB لجسم الطلب ومحدد معدل منفصل لنقطتي تسجيل الدخول والتسجيل، بالإضافة إلى حدود الـChat الموجودة.
4. `backend/app/accounts.py`: تفعيل WAL للـSQLite وتحقق من بنية الأيام عند حفظ الرحلة (الترتيب، التكرار، المدينة، حجم المحطات، 30 يومًا كحد أقصى). الأيام الفارغة تُقبل كمسودة قديمة ولا تعتبر برنامجًا مكتملًا.
5. حفظ الرحلات والمحادثات: دعم `If-Match` الاختياري برمز `updated_at` لرفض كتابة نسخة قديمة (`409`) دون إفساد البيانات. واجهة حفظ المحادثة الآن ترسل هذا الرمز، وتحدّثه بعد الحفظ أو الاسترجاع. بعض العملاء القدامى لا يستخدمون هذه الحماية بعد؛ يلزم فرضها عند استكمال ترحيلهم.
6. `backend/app/commerce.py`: منع إدخال روابط شركاء `localhost` أو العناوين الداخلية/IP المباشرة ضمن عروض الإحالة. روابط HTTPS الخارجية تحتاج مراجعة بشرية رغم هذه الحماية.
7. `backend/app/main.py`: في بيئة `APP_ENV=production`، لا يعتمد النظام على `X-Real-IP` إلا إذا أُدرج عنوان الـProxy الفعلي في `TRUSTED_PROXY_IPS`؛ في غير ذلك يستخدم عنوان الاتصال المباشر. لا بد من تقييد الوصول المباشر للـBackend.
8. `scripts/check_no_secrets_v75.py`: فحص استرشادي لمفاتيح API محتملة وملفات إعدادات خاصة قبل النشر، وتكامل مع GitHub Actions.
9. `backend/tests/test_proactive_reliability_v75.py`: مجموعة اختبارات أمن واعتمادية وهجوم على البيانات، مع الاحتفاظ بجميع الاختبارات السابقة.

## مخاطر قائمة تمنع اعتماد إطلاق تجاري

- **P0**: إكمال `npm ci && npm test && npm run lint && npm run build` واختبار متصفح على سطح المكتب والموبايل. فحص الصياغة لا يضمن سلامة تشغيل React.
- **P0**: اختبار Gemini الحي بمجموعة حالات متعددة اللغات، وقياس دقة المصادر والردود على الحالات الحساسة باستخدام مفتاح جديد محفوظ على الخادم فقط.
- **P0**: تخزين دائم حقيقي ونسخ احتياطية واسترجاع مجرَّب. Render Free لا يوفر ضمان بقاء بيانات SQLite بعد إعادة النشر.
- **P0**: تحقيق أمان نشر الإنتاج: HTTPS؛ سياسات CSP وCORS حسب النطاق؛ تدقيق الثغرات في الاعتمادات؛ تتبع أخطاء مجهول الهوية؛ مراقبة حدود استهلاك Gemini؛ منع وصول مباشر يتجاوز الـReverse Proxy.
- **P1**: تطوير نظام صلاحيات إداري لكل مستخدم مع جلسات فردية وMFA بدل مفتاح إداري مشترك طويل الأجل؛ مراجعة وتسجيل تغييرات المحتوى والشركاء.
- **P1**: مهاجرة SQLite إلى PostgreSQL قبل استقبال زيارات وكتابات متزامنة بكثافة؛ ضبط المعاملات والتحديثات التنافسية لكل موارد الـAPI.
- **P1**: تقييم RAG بمصادر سياحية محدثة وآمنة، ومكافحة Prompt Injection في بيانات المصادر ومحادثات المستخدم، ومنع تلف حالة الرحلة بعد أي استدعاء AI.
- **P1**: اختبار Nginx الحقيقي، وحدود الطلبات بدون Content-Length، والـRate Limit الموزّع؛ الحالي داخل ذاكرة عملية واحدة.
- **P1**: سياسات خصوصية وحذف بيانات وضبط صلاحيات المستخدمين، وتراخيص صور ومحتوى وشراكات مع مؤسسات مرخّصة.
- **P2**: اختبار الوصول Accessibility وSEO وCore Web Vitals للموقع المنشور، وأجهزة الموبايل، والمحتوى السياحي الشامل.

## معايير قبول الإصدار

1. لا أخطاء P0/P1 مفتوحة في تدفقات الحساب والرحلة والـAI الأساسية.
2. جميع اختبارات الـBackend والـCI وReact Build وBrowser E2E خضراء على **GitHub**.
3. اختبار Live Gemini باستخدام مفتاح آمن من بيئة التشغيل دون مشاركته في المحادثة.
4. نشر نسخة Staging، ثم Smoke Tests ونسخ احتياطي واسترجاع، ثم مراجعة أمن مستقلة قبل فتح الحسابات للجمهور.
5. أي فشل مستقبلي يضاف كاختبار Regression بعد إصلاح جذره؛ لا تغيّر معايير التقييم لإخفاء مشاكل المنتج.
