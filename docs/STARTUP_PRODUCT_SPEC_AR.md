# Masr Guide AI — رؤية منتج Startup  (ليست وظائف منفذة بالكامل)

## مشكلة المستخدم وميزة المنتج
ليس الهدف واجهة ChatGPT عن مصر. يريد المسافر أن يحدد قيودًا حقيقية (الأيام، المجموعة، الميزانية، ما يغطيه السعر، الوصول والمغادرة)، ثم يستلم *Trip Workspace* مرتبًا، ويمكنه إعادة التخطيط وحفظ نسخ منه.

## رحلة المستخدم المستهدفة
1. اكتشف مصر: Home تحتوي بحث وجهات واضح، قصص وتجارب وأزرار «ابنِ رحلتك»؛ ليست نافذة Chat وحدها.
2. Onboarding قصير: بلد المغادرة، مدة الزيارة، تاريخ السفر، عدد البالغين والأطفال، ميزانية وعملتها **وماذا تشمل**، اهتمامات، وتفضيلات النقل.
3. Itinerary Workspace: تقويم/Timeline لكل يوم، خريطة محطات، عرض ميزانية مفصّل مع توضيح مستوى الثقة، وتعديلات مرئية.
4. AI Consultant: محادثة تشرح المفاضلات وتسأل فقط عما يؤثر في القرار، ويمكنها استدعاء أدوات تخطيط وإعادة تخطيط مع تأكيد التغيير قبل تطبيقه.
5. During-trip mode: نسخة محمولة، مشاركة خطط مع المجموعة، وتنبيهات اختيارية بعد ربط مصادر فعلية.

## محرك المنتج المطلوب
- LLM Orchestrator: استخراج نوايا بتنسيق JSON محكوم بـSchemas، واستدعاء أدوات server-side. لا نعتمد على نص LLM لإثبات الميزانية.
- Planning Engine: قيود وأولويات محددة؛ أوقات انتقال مدعومة بمصدر Routing مرخص، وثبات الحجوزات إن وجدت.
- Verified Tourism Catalog: بيانات معالم، تجارب، مناطق شاطئية، ساعات عمل، لوجستيات، مصادر وتواريخ تحديث ورخص صور.
- Budget Engine: عملات ونطاقات أسعار وتكاليف نقل وإقامة وطعام وأنشطة؛ يقول «لا تتوفر تقديرات موثوقة» عند غياب البيانات.
- Trip Persistence: حسابات أو Guest Trip IDs آمنة، حفظ على السيرفر، سجل تعديلات، مشاركة بإذن؛ البيانات الحالية في sessionStorage فقط.
- Quality & Observability: مقاييس اكتمال الرحلات، فشل النموذج، تكلفة/جلسة، زمن الاستجابة، تقييم جودة/صحة المراجع، حدود الاستهلاك.

## MVP القابل للاختبار التجاري
- برنامج 7–30 يومًا مع تعديل مدن وأيام وقيود أساسية.
- تجربة عربي/إنجليزي متسقة في الموقع كله؛ لا يلزم لغات كثيرة قبل اختبار الجودة.
- صفحات Home / Destinations / Planner / Trip Workspace / AI Consultant واضحة؛ فصل Workspace عن صفحة المحادثة.
- حفظ برنامج قابل لاستعادته ورابط مشاركة بصلاحية محدودة.
- دقة مصادر الأماكن والتنقلات، وبيان عدم توفر أسعار حية عند الحاجة.
- اختبار المستخدمين مع 10–20 سائحًا وتسجيل الأخطاء وليس فقط اختبارات الوحدات.

## مؤشرات قياس النجاح
- نسبة إكمال طلب الرحلة، وعدد التعديلات حتى الوصول لخطة مقبولة.
- رضا السائح بعد اختبار الرحلة، وصحة الأسماء والطرق والروابط والمصادر.
- زمن إنشاء الخطة وتكلفة Gemini لكل جلسة وحصة الرفض.
- نسبة الاستخدام مجددًا أو مشاركة الخطة، ثم استعداد الدفع بعد مقابلات حقيقية.

## شروط قبول الإصدار القادم
1. تجربة محمولة Responsive كاملة + Build/Browser E2E مثبتان.
2. 20 يومًا بأسبوع بحر وباقي القاهرة، وباللغة العربية، دون تكرار زيارات أو فقد الأيام.
3. لا يدعي توافق الرحلة مع 15 ألف جنيه دون تسعير حقيقي؛ يطلب نطاق التغطية وعدد المسافرين.
4. تعديل الرحلة من المحادثة يغيّر Trip Workspace ويحفظ الحالة ونسخة سابقة.
5. كل مرجع قابل للنقر وصحيح الصلة ولا يُوصف بأنه موثق رسميًا إذا لم يُتحقق منه.
6. حماية مفاتيح Gemini وحدود الطلبات ومراقبة الاستهلاك وحقوق الصور.

## النشر والبنية
- GitHub يخزن الكود ويشغّل اختبارات CI؛ **ليس خادم FastAPI في حد ذاته**.
- GitHub Pages يستضيف صفحات ثابتة فقط. يحتاج Backend إلى خدمة تشغيل Python منفصلة وقاعدة بيانات دائمة عند إضافة حسابات؛ افحص شروط الحصة المجانية قبل الاعتماد عليها تجاريًا.
- أبق المستودع Private مؤقتًا ريثما تُحسم الملكية الفكرية وترخيص صور ومحتوى الهاكاثون.

هذا المستند مواصفات تطوير، وليس تصريحًا بأن الخصائص المذكورة كلها تعمل.
